# Troubleshooting & Runbook — Outage Automation

This runbook covers diagnostic procedures, common error states, and recovery steps for operators managing Outage Automation.

---

## Quick Diagnostic Commands

Run from the repository root:

```bash
# 1. Check system status & recent provider ingest results
python python_system/run.py status

# 2. Check state data quality and schema compliance
python python_system/run.py lint-events --strict

# 3. Check customer subscription mappings against approved regions
python python_system/run.py lint-customers

# 4. Verify parser test fixtures against current parser code
python python_system/run.py verify-fixtures --strict

# 5. Check dashboard HTTP server liveness (unauthenticated)
curl -fsS http://127.0.0.1:8765/api/health
```

## Common Issues & Recovery Procedures

### 1. HTTP 503 — "state/.lock is locked"

**Symptom:**
CLI commands exit with code 2 or dashboard returns `503 locked`.
Message: `locked by pid <PID> since <TIMESTAMP>`

**Cause:**
Another process is currently updating state, or a previous process died abruptly without cleaning up `state/.lock`.

**Recovery:**
1. Verify if the PID is still running:
   ```bash
   ps aux | grep <PID>
   ```
2. If the PID is active, wait for the ingest run to finish (usually <10 seconds).
3. If the process is dead (stale lock):
   ```bash
   # CLI automatically clears stale locks if the PID does not exist:
   python python_system/run.py status
   # Or manually remove if confirmed stale:
   rm -f state/.lock
   ```

---

### 2. HTTP 429 — "Too Many Requests" (IP Lockout)

**Symptom:**
Clients (including loopback `127.0.0.1`) receive `429 Too Many Requests` with header `Retry-After: <seconds>`.

**Cause:**
Brute-force protection engaged after 5 consecutive failed authentication attempts within 60 seconds.

**Recovery:**
1. Wait for the lockout timer to expire (default: 15 minutes / 900 seconds).
2. Or restart the dashboard service to reset in-memory rate limits:
   ```bash
   systemctl restart outage-automation-dashboard.service
   ```
3. Inspect auth logs in journald:
   ```bash
   journalctl -u outage-automation-dashboard.service -n 50 | grep AUTH_
   ```

---

### 3. HTTP 401 — "Unauthorized"

**Symptom:**
Requests to `/api/dashboard`, `/api/customers`, `/api/regions`, or `/dashboard` return 401.

**Checks:**
1. Check configured password file location in `/etc/systemd/system/outage-automation.env`.
2. Inspect the password file permissions (must be readable by dashboard user, e.g. `chmod 600`):
   ```bash
   ls -la /etc/outage-automation/dashboard.pw
   ```
3. Rotate password if compromised:
   ```bash
   ./python_system/bin/oa-rotate-password.sh
   ```

---

### 4. Systemd Timer or Service Failures

**Diagnostics:**
```bash
# Check timer status
systemctl list-timers 'outage-automation*'

# View service logs
journalctl -u outage-automation.service -n 100 --no-pager
journalctl -u outage-automation-dashboard.service -n 100 --no-pager
```

**Common Gotchas:**
- `${OA_ROOT}` expansion: Ensure systemd unit wraps commands in `/bin/sh -c 'exec "${OA_ROOT}/..."'`.
- Permissions: Verify the service user has read/write permissions to `state/` and read permissions to `approved-regions.csv`.

---

### 5. Disk Headroom & Prune Scratch Cleanup

**Symptom:**
Services fail with `OSError: [Errno 28] No space left on device`. Root filesystem is at or near 100%.

**Cause:**
Large audit log (`events.ndjson`) combined with unpruned scratch files (`events.prune.tmp`) from previous interrupted runs.

**Safeguards & Recovery:**
1. Hardened pruner automatically cleans `events.prune.tmp` via `try ... finally` and requires at least 1.2x file size in available free space before creating temporary streaming files.
2. The prune systemd unit enforces `ExecStopPost=/bin/rm -f .../events.prune.tmp`.
3. Check and clean any lingering temporary files:
   ```bash
   rm -f state/*.tmp
   df -h /
   ```
4. Check available LVM Volume Group space and expand if required:
   ```bash
   vgs
   lvextend -L +XG -r /dev/ubuntu-vg/ubuntu-lv
   ```

### 6. Data Recovery from Backups

**Restic Restores:**
```bash
# Export repo and password
export OA_RESTIC_REPO="/var/backups/oa-restic"
export OA_RESTIC_PASSWORD_FILE="/etc/outage-automation/restic.pw"

# List snapshots
restic -r "$OA_RESTIC_REPO" snapshots

# Restore latest snapshot to /tmp/restore
restic -r "$OA_RESTIC_REPO" restore latest --target /tmp/restore
```

## 7. SSL / TLS Troubleshooting

### Browser Warns "Your connection is not private" / Self-Signed Certificate
- The default certificate generated by `oa generate-cert` is a self-signed SAN certificate.
- To access: click **Advanced -> Proceed to <host> (unsafe)**.
- To eliminate browser warnings on corporate workstations:
  - Install the generated `/etc/outage-automation/dashboard.crt` into the workstation's Trusted Root Certification Authorities store.
  - Or provide a corporate CA-signed certificate:
    ```bash
    cp corporate.crt /etc/outage-automation/dashboard.crt
    cp corporate.key /etc/outage-automation/dashboard.key
    chmod 600 /etc/outage-automation/dashboard.key
    sudo systemctl restart outage-automation-dashboard.service
    ```

### Inspecting / Renewing the Certificate
- Check certificate expiry and Subject Alternative Names:
  ```bash
  openssl x509 -in /etc/outage-automation/dashboard.crt -text -noout | grep -E 'Not After|DNS:|IP:'
  ```
- Regenerate a new 10-year self-signed SAN certificate:
  ```bash
  oa generate-cert --cert /etc/outage-automation/dashboard.crt --key /etc/outage-automation/dashboard.key --host <your-host-ip>
  sudo systemctl restart outage-automation-dashboard.service
  ```
